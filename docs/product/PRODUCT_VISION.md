# Product Vision

Yantra exists to become a Windows-first autonomous software engineering operating system for real repository work. The product vision is not to recreate a chat surface, an IDE clone, or a code-completion shell; it is to provide a governed engineering workspace where missions can be planned, approved, executed, verified, and completed with the support of specialised agents.

## Product position

Yantra should feel like a serious desktop engineering product built for sustained use. It must give a user one place to understand repository state, define a mission, delegate execution safely, review outcomes, and continue work without losing context.

## Long-term direction

The long-term direction is a product where the workspace is the durable operating surface and missions are the main unit of progress. Agents, memory, knowledge, verification, and governance exist to support that mission-centric workflow rather than compete with it.

## What Yantra is not

Yantra is not:

- a generic chat application,
- a wrapper around LLM providers,
- an IDE replacement whose main value is editing text,
- a cross-platform-first product,
- an autonomy system without human checkpoints.

## User promise

A user should be able to open a workspace, understand what matters, define or resume a mission, supervise agent work, verify outcomes, and keep moving without reconstructing context from scratch.

## Product outcomes

Yantra should:

- reduce engineering coordination overhead,
- make mission progress visible,
- keep approvals and governance explicit,
- preserve repository context across sessions,
- support reliable execution and verification before completion.

## Phase direction

The current product direction prioritises a Windows desktop application with a minimal, clean, mission-first interface. Early phases should establish the product shell, workspace model, provider layer, mission flow, memory and knowledge grounding, agent orchestration, and verification surfaces in a way that preserves long-term maintainability.

## Vision constraint

The product vision only succeeds if the repository, architecture, and implementation remain aligned with the PRD. If any convenience shortcut would make Yantra look like a chat-first app, an uncontrolled agent shell, or a dense IDE clone, that shortcut should be rejected.
